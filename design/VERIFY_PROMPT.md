# 최종 검증 프롬프트 (Codex에 그대로 붙여 넣기)

UI 작업이 끝났을 때, 또는 PR 올리기 전에 아래 프롬프트를 그대로 실행한다. 결과 표를 PR 본문에 붙인다.

---

```
너는 Probe QA 프론트엔드의 디자인 검수자다. 지금부터 구현 결과를 `design/DESIGN.md`와 `design/screens/` 레퍼런스에 대조해 검증한다. 새 기능을 추가하거나 디자인을 개선하지 않는다. 어긋난 곳을 찾아 고치는 것만 한다.

절차:
1. `design/DESIGN.md`를 처음부터 끝까지 읽는다. 특히 §2 컬러, §3 타이포, §5 상태 표기, §7-1 버튼 라벨, §8-1 금지 패턴.
2. 이번 변경으로 영향받는 모든 화면과 상태(빈 상태, 로딩, 오류, 펼침/접힘)를 1440×900 뷰포트에서 렌더링해 스크린샷을 찍는다. 스크린샷 없이 코드만 보고 판단하지 않는다.
3. 각 화면을 가장 가까운 `design/screens/Mxx.png`와 나란히 놓고 아래 항목을 하나씩 확인한다. 항목마다 PASS / FAIL과 근거(파일:줄 또는 스크린샷 좌표)를 적는다.

검사 항목:
A. 컬러 — 페이지에 `design/tokens.css`에 없는 색이 있는가. 유채색(파랑·초록·빨강·노랑)이 텍스트·배지·보더·배경 어디에든 있는가.
B. 타이포 — Pretendard 외 폰트, 700 이상 웨이트, 스케일 외 px가 있는가. JetBrains Mono가 적용된 텍스트에 한글이 포함되어 있는가.
C. 형태 — box-shadow가 있는가. 라운드가 pill / 14 / 12 / 10 / 8 / 6 외의 값인가. 카드 안에 카드가 있는가. 왼쪽 컬러 보더가 있는가.
D. 버튼 — 화면에 primary(검정 채움) 버튼이 2개 이상인가. 새로고침·다운로드·재실행·초기화가 primary인가. 라벨이 §7-1 표에 없는가. 버튼에 아이콘이 붙어 있는가.
E. 상태 표기 — 상태(성공/실패/진행/대기)가 색으로 표현되어 있는가. §5 표의 글리프·굵기와 다른가. 완료 상태가 배너·카드·진행 바로 남아 있는가.
F. 표 — 헤더와 셀의 x 시작점이 다른가. 셀 텍스트가 2줄로 꺾이는가. 행 링크 안에 링크가 중첩되어 있는가. 셀렉트에 네이티브 화살표가 보이는가.
G. 폼 — 브라우저 기본 검증 툴팁이 뜨는가. 오류가 빨간 배경 박스로 표시되는가. 같은 폼이 2개 이상 펼쳐져 있는가.
H. 밀도 — 반복 항목 5개 이상이 전부 펼쳐져 있는가. 필터·툴바가 박스로 감싸져 있는가. 설명 문장이 라벨마다 붙어 있는가.
I. 줄바꿈 — 의도하지 않은 줄바꿈이 있는가 (제목, 메타, 표 셀, 버튼 라벨, 카드 제목). 있으면 위치를 적는다.
J. 레퍼런스 대조 — 같은 종류의 화면이 `design/screens/`에 있는데 구조(블록 순서, 열 구성, 카드 여부)가 다른 곳이 있는가.
K. 폰트 로드 — 실제 렌더링에서 Pretendard 400/500/600과 JetBrains Mono 400/500이 로드되었는가. 브라우저 콘솔에서 `[...document.fonts].map(f => f.family + ' ' + f.weight + ' ' + f.status)`를 실행해 5개가 모두 loaded인지, Pretendard 700 이상이 로드되지 않았는지 확인한다. 폰트가 CDN(Google Fonts 등)에서 오는가 — `design/fonts/`의 파일에서 와야 한다. `design/screens/FontCheck.html`을 열어 하단 결과가 모두 ✓인지 확인하고 그 스크린샷을 첨부한다.

출력 형식:
| 항목 | 결과 | 위치 | 내용 |
|---|---|---|---|
| A 컬러 | PASS/FAIL | 파일:줄 | 한 줄 설명 |
... K까지.

FAIL 항목은 전부 고친 뒤 2번부터 다시 실행한다. 모두 PASS가 될 때까지 반복한다. 고칠 수 없거나 디자인 판단이 필요한 항목은 고치지 말고 "기획자 확인 필요"로 표시한다.
마지막에 수정 전/후 스크린샷을 화면별로 나란히 첨부한다.
```
